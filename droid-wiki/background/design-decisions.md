# Design decisions

Strata's code follows a few library-wide design choices that are applied consistently across modules. This page lists each choice, the files that show it, and the reasoning where the code or documentation states it. Where the reason is inferred rather than written down, the text says so.

For how to apply these patterns when writing code, see [Patterns and conventions](../how-to-contribute/patterns-and-conventions.md).

## Immutable types and Joda-Beans

Almost every public type is immutable, and class documentation usually ends with "This class is immutable and thread-safe." Types that carry many properties (trades, products, conventions, curve definitions) are Joda-Beans: fields are declared with `@BeanDefinition` and `@PropertyDefinition`, and the code generator writes the meta-bean, builder, `equals`, `hashCode` and `toString` between `AUTOGENERATED START` and `AUTOGENERATED END` markers. About 563 Java files and 59 Scala files contain such a block.

Examples:

- `modules/market/src/main/java/com/opengamma/strata/market/observable/QuoteId.java` (light bean)
- `modules/basics/src/main/scala/com/opengamma/strata/basics/ImmutableReferenceData.scala` (Scala bean, hand-maintained)
- `modules/basics/src/main/scala/com/opengamma/strata/basics/currency/CurrencyAmount.scala` (plain immutable class)

Immutable values can be shared between threads without locking, which the multi-threaded `CalculationRunner` depends on, and Joda-Beans gives every bean the same reflection-free metadata, builders and XML/JSON/binary serialization. That combination is the likely motivation; the code does not spell it out in one place. See [Joda-Beans and serialization](../features/joda-beans-and-serialization.md).

## Resolve before pricing

Trades and products refer to reference data by identifier (holiday calendars, securities). Before pricing they are resolved against `ReferenceData`, producing a "resolved" form such as `ResolvedSwap`. The contract is documented on `Resolvable` in `modules/basics/src/main/scala/com/opengamma/strata/basics/Resolvable.scala`:

> The resolving process will take each identifier, look it up using the `ReferenceData`, and return a new "resolved" instance. Typically the result is of a type that is optimized for pricing.

The same file warns that resolved objects are bound to the reference data at the time of resolution: if a holiday is added later, the resolved form is not updated, so caching it needs care. Related types are `modules/basics/src/main/scala/com/opengamma/strata/basics/ReferenceData.scala`, `ReferenceDataId.scala` beside it, `modules/product/src/main/java/com/opengamma/strata/product/ResolvableTrade.java` and `modules/product/src/main/java/com/opengamma/strata/product/ResolvedTrade.java`.

Keeping schedule generation and holiday adjustment out of the pricers, and resolving once before pricing many scenarios, is the evident benefit. See [Pricing a trade](../features/pricing-a-trade.md) and [Reference data and configuration](../features/reference-data-and-configuration.md).

## Results instead of exceptions in the engine

The calculation engine computes a grid of trades by measures. One bad trade or missing quote should not stop the rest, so engine code returns `Result<T>` values (`modules/collect/src/main/scala/com/opengamma/strata/collect/result/Result.scala`) holding either a value or a `Failure` with `FailureItem`s.

`CalculationFunction.calculate` in `modules/calc/src/main/java/com/opengamma/strata/calc/runner/CalculationFunction.java` returns `Map<Measure, Result<?>>`, and `CalculationTask` in the same package converts exceptions thrown by a function (missing market data, missing reference data, unsupported operations, other errors) and measures the function did not return into `Result.failure(...)` cells with a `FailureReason`. Outside the engine, ordinary exceptions are used (`IllegalArgumentException` from `ArgChecker`, `MarketDataNotFoundException` in `modules/data`).

## Calculation engine separate from pricers

`modules/calc/src/main/java/com/opengamma/strata/calc/package-info.java` draws the line:

> The strata-pricer module provides the ability to calculate results for a single trade, single measure and single set of market data. The strata-calc module provides the ability to calculate results for many trades, many measures and many sets of market data.

The module POMs enforce it. `modules/calc/pom.xml` depends only on `strata-collect`, `strata-basics` and `strata-data`; it knows nothing about products, curves or pricers. `modules/pricer/pom.xml` does not depend on `strata-calc`. The two meet in `modules/measure`, whose POM depends on both, and whose `*TradeCalculationFunction` classes adapt pricers to the engine. `modules/measure/src/main/java/com/opengamma/strata/measure/StandardComponents.java` wires the standard set together.

A plausible reading is that this lets the pricers be used directly, without the engine, and lets the engine run any kind of target. The engine works with `CalculationTarget`, not with `Trade`. See [calc](../modules/calc.md), [measure](../modules/measure.md) and [Architecture](../overview/architecture.md).

## Point sensitivities, then parameter sensitivities

Pricers return sensitivities in two stages:

- `PointSensitivities` (`modules/market/src/main/java/com/opengamma/strata/market/sensitivity/PointSensitivities.java`): sensitivities to individual points on a curve that the pricer actually queried, for example one entry per date on the forward and discount curves.
- `CurrencyParameterSensitivities` (`modules/market/src/main/java/com/opengamma/strata/market/param/CurrencyParameterSensitivities.java`): sensitivities to the parameters of curves and surfaces, such as their nodes.

The conversion is done by the market data provider, for example `RatesProvider.parameterSensitivity(PointSensitivities)` in `modules/pricer/src/main/java/com/opengamma/strata/pricer/rate/RatesProvider.java`. Pricers therefore only need to know which points they read, not how a curve is parameterized or interpolated; the curve representation can change without touching pricers. That rationale is inferred from the structure. See [Sensitivities](../features/sensitivities.md).

## Extensible named types configured by INI files

Day counts, holiday calendars, indices, roll conventions and trade conventions look like enums but are open sets. They implement `Named` and are registered through `ExtendedEnum` (`modules/collect/src/main/scala/com/opengamma/strata/collect/named/ExtendedEnum.scala`), which reads an INI file named after the type, such as `modules/basics/src/main/resources/META-INF/com/opengamma/strata/config/base/DayCount.ini`. The INI file names provider classes, alternate names and external name groups.

`ResourceConfig` (`modules/collect/src/main/scala/com/opengamma/strata/collect/io/ResourceConfig.scala`) merges files of the same name from the `base`, `library` and `application` directory groups, so a library or application can add values, or rename and remove sections, without changing Strata. The README in `modules/basics/src/main/resources/META-INF/com/opengamma/strata/config/README.md` describes the directories and the `com.opengamma.strata.config.directories` system property.

## Java 8 API level

The Java modules compile with `maven.compiler.release` 8, set by the `forcejavaversion` profile in `modules/pom.xml` whenever the build JDK is 9 or later. `AGENTS.md` and `.factory/skills/code-conventions/SKILL.md` repeat the rule: Java source must stay Java 8 compatible, with no post-8 APIs.

On the `auto_model_migration` branch this applies only to the Java modules. `collect` and `basics` are Scala and emit Java 17 bytecode, so the build and every user now need JDK 17, even though the Java modules still target the Java 8 API. The migration kept javac at release 8 because changing it globally would alter overload resolution in unrelated Java code (recorded in `step_by_step_guide.md`). See [Scala migration](scala-migration.md).

## `impl` packages are not public API

`modules/pricer/src/main/java/com/opengamma/strata/pricer/impl/package-info.java` says code in the package "may change in a non-backwards compatible way". `AGENTS.md` describes the `impl` packages in `pricer` and `loader` as private implementation details. The aggregate Javadoc in `modules/pom.xml` excludes `com.opengamma.strata.loader.impl`, `com.opengamma.strata.math.impl` and `com.opengamma.strata.pricer.impl`, so those packages do not appear in the published API documentation.

## `double` for amounts, `BigDecimal` only for rounded money

`CurrencyAmount` (`modules/basics/src/main/scala/com/opengamma/strata/basics/currency/CurrencyAmount.scala`) holds a `double`. Its documentation explains the choice: the name avoids "Money" because that "would imply it was a suitable choice for accounting purposes, which it is not", the design was "chosen primarily for performance reasons", and "Using a `BigDecimal` is markedly slower". It accepts small floating point errors such as `0.1 + 0.2` giving `0.30000000000000004`.

`Money` (`modules/basics/src/main/scala/com/opengamma/strata/basics/currency/Money.scala`) is the alternative: it only exposes amounts rounded to the currency's minor units, using `BigDecimal` with half-up rounding. Analytics such as `MultiCurrencyAmount`, `CurrencyAmountArray` and the pricers work in `double`.
